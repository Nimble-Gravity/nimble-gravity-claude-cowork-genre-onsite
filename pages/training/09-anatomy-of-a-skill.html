Anatomy of a Skill

You just walked the status report by hand and held every step in your head. A skill is that list written down in a file Cowork reads — so next Friday you don't remember any of it, and neither does the colleague you hand it to. This lesson covers what goes in the file, straight from Anthropic's own standards, and then you go and repair four broken ones.

Skills & Everyday Workflows · ~50 min
01 — Name the steps you just did

Get the job out of your head and onto a page

Before any file format, write down what you actually did in Lesson 1. Three things, half a page. Do this now, at your desk — five minutes, on paper or in a file, and you'll build on it in the vault this afternoon. Everything after this is just that half page in the shape Cowork reads, and a skill can only be as good as this list — a vague step in, a vague draft out.

The steps, in order

Read the three sources, draft the four sections, cite every figure, flag where the documents disagree, never fill a gap. Write them as instructions to a capable new colleague, not as notes to yourself.

Where the inputs live

Name the folder, the mailbox, or the system each step reads from. Vague inputs are the most common reason a skill underperforms — it can't find what you didn't name, so it improvises.

Good output vs. bad output

A line on what a strong result looks like and a line on a weak one. You already have both from Lesson 1: the draft you'd have sent, and the thing you had to correct. These become the examples in the skill and the cases you test it against.

🍳
Skills vs. agents vs. connectors — skip the taxonomy

A skill is a recipe Cowork follows. That's all you need today. There is a whole vocabulary underneath, and none of it changes what you're about to write. If it comes up, ask; otherwise leave it to Day 3, where the only part that matters to you is how a skill gets distributed and approved.

02 — The top of the file

The description does most of the work

A skill is a folder with one file in it, SKILL.md, on the open Agent Skills standard. The top of that file is two fields. At startup Claude loads only each skill's name and description — that's what it reads to pick the right skill out of dozens, so a clear description is what gets your skill to fire when it should.

name

Up to 64 characters, lowercase letters, numbers, and hyphens, and no reserved words like "anthropic" or "claude." Anthropic suggests the gerund form, such as processing-pdfs or analyzing-spreadsheets. Yours would be drafting-status-reports.

description

Third person, up to 1024 characters. Say what the skill does and when to use it, with the words that should trigger it: "...Use when working with PDF files or when the user mentions PDFs, forms, or document extraction." Claude tends to under-trigger, so write it almost too eagerly.

03 — The body

"Concise is key. The context window is a public good."

That's Anthropic, word for word. Add only the context Claude doesn't already have, and keep the file short so it stays fast to read and simple to maintain. Your half page from section 01 is already close to the right length; the temptation to pad it is the thing to resist.

Keep it under 500 lines

Use progressive disclosure

Treat SKILL.md as a table of contents that points to detail files Claude opens only when it needs them. Keep references one level deep, since Claude may only partly read nested ones, and add a table of contents to any reference file over 100 lines.

Split the body into separate files as it nears 500 lines.
Explain the why

Don't fall back on ALL-CAPS

Instead of MUST, ALWAYS, and NEVER, state the rule and then say why, so Claude can generalize from it. Give a few real input and output examples, offer a sensible default with a way out, and use forward-slash paths.

Make instructions more specific as the task gets more fragile.
04 — Evaluation-driven development

"Create evaluations before writing extensive documentation."

Anthropic's words again, and the one instruction people ignore. You build a skill by testing it, not by writing careful prose and hoping. For this audience it lands as something familiar: you wouldn't sign off a model without a back-test, and a skill is no different.

01
Evals first, then minimal docs
Find the gaps by running the task without the skill — you did this in Lesson 1. Write at least three test scenarios, set that as your baseline, then add only the instructions needed to pass.
02
Test across models
Run your tests on Haiku, Sonnet, and Opus. A skill that only works on the largest model isn't finished, and your colleagues will not all be on the same one. This is the one time you move off Sonnet deliberately — you're testing the skill, not doing the work — and you set the selector back afterwards.
03
Write with one Claude, test with another
One Claude helps you draft the skill; a fresh Claude uses it cold, with none of your context. There's no built-in eval runner, so "run it cold three times and grade it" is the eval.
📐
Use the doc as your rubric

The frontmatter, body, and evals rules on this page come from Anthropic's skill-authoring best-practices doc on platform.claude.com, current as of June 2026. Use it as the grading rubric for every skill you ship, and check it again before each cohort, since it changes.

05 — Getting from a walk to a file

You don't write it from a blank page

Most first skills start as text that already works — the ask you pasted in Lesson 1, refined once. Hand that to Claude and ask it to make it reusable, then harden it. Read these four now; you run them in the vault, not at your desk — they are the loop you'll be inside for the whole forty minutes, so it's worth knowing them before the clock starts. The third is the one people skip.

1
Describe the workflow in plain words and ask Cowork for a skill. Paste your half page from section 01 and say what should trigger it — "turn this into a skill that fires whenever I ask for a status report".
You're not learning a file format, you're handing over something you already do, which is why the half page matters more than any syntax on this page.
2
Read the draft against the rules above before you trust it. Is the description third person and full of the words you'd actually type? Is the body short, with the why alongside each rule?
First drafts reliably over-explain and under-trigger, and both of those show up in the first ten lines, so this check costs you a minute rather than a rewrite.
You can point at the sentence that makes it fire.
3
Test it cold in a fresh session, with and without the skill. Run the same ask both ways and grade the difference.
A fresh session has none of the conversation you just had, which is exactly the condition your colleague will use it in — and if the two runs look the same, the skill isn't earning its place.
It fires on its own, without you naming the skill.
4
Fix only what the test caught, then save the skill file. Add the one instruction that closes the gap and nothing else.
Every line you add that no test demanded is a line someone maintains later and nobody can explain.
06 — A worked example

A small, finished skill: memo generation

The same shape as your status report, finished and held against the rules above: draft a document from source material, cite everything, flag the gaps, hand a human a draft to sign. Its description is keyword-rich and third person, the body is well under 500 lines, it carries a good-versus-bad example and a guardrails block, and it points one level deep at a format file. The file itself is on this lesson page rather than on the slide — forty lines of monospace does not project. Open the page, read it there, and hold your own first skill to it.

memo-generation / SKILL.md 
---
name: memo-generation
description: Drafts a structured business memo from rough source material — meeting notes, an email thread, or a few bullet points — in the team's standard format and voice, leaving a clear draft for a person to review and sign off. Use when someone asks to "write a memo", "turn these notes into a memo", "draft a summary memo", or "put this in memo form", especially for recurring internal or client-facing memos in regulated, document-heavy work.
---

# Memo Generation

Turn rough input into a clean, well-structured memo draft. Analysts and associates lose
hours to this; the structure rarely changes, so it is an ideal first skill. The output is
always a draft for a human to review — never a final, never sent automatically.

## How to draft

1. Read everything first. Understand the whole input before you summarize.
2. Lead with the bottom line. The first sentence states the conclusion or the ask.
3. Use the standard sections: Purpose, Background, Key Points, Recommendation / Next Steps.
   If no format is given, use reference/memo-format.md and say you used the default.
4. Cite the source for any figure or claim — name the file, email, or note.
5. Flag gaps, don't fill them. Unsupported section -> [NEEDS INPUT: ...].
6. Match the house voice if a voice-profile exists; otherwise keep it plain and tight.

## Good vs. bad output

Good — bottom line first; every claim traceable to a source; gaps flagged; one page;
ready for a reviewer to approve with light edits.

Bad — buries the ask in paragraph three; invents a number that isn't in the source;
fills an empty section with filler; reads like a chat transcript; needs a full rewrite.

## Guardrails

- Never present the memo as final or send it anywhere. It is a draft for review.
- Never fabricate figures, names, or quotes. Unknown -> [NEEDS INPUT: ...].
- Keep it to one page unless the user asks for more.

07 — The lab

The Skill Vault

The lab is an escape room, and each room is a skill repair. You're locked in a vault with four skills that don't work properly; fixing each one produces a code that opens the next door. Teams of two or three, one 40-minute clock, and a leaderboard at the front of the room.

Four rooms, four repairs

The Inherited Skill — run one somebody else wrote. The Broken Trigger — a skill that never fires, because of its description. Forge Your Own Key — write one from scratch. The Playbook Door — chain two of them through a single ask.

The code is in the work

Each unlock code comes out of the artifact the repair produces, so there's no guessing your way through — the door opens because the skill now works. Two hints per room; the second one costs you two minutes.

Why an escape room

Because reading four skills and repairing them teaches the anatomy faster than writing one from a blank file, and because the failure modes in the vault are the ones you'll hit at your desk next week. Nobody's score leaves the room.
