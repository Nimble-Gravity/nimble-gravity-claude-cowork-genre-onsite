Use Cowork Lab

Run a real use case from your industry through start to finish. Pick a task, hand it off on the right model and permission mode, steer the plan, and come away with a deliverable you'd be willing to ship. Along the way, note the part you'd want to turn into a reusable skill.

Exercise · ~40 min
00 — Before you write your first prompt

Five principles from Anthropic's Cowork guidance

The prompts on this page are already written this way — read them and you'll see all five.

  1. Outcome, not steps. Cowork builds its own plan. Describe what the finished output looks like, not the steps to get there.
  2. Say what done looks like. Write your acceptance test before you paste the prompt. If you cannot describe a passing output in one sentence, the prompt is not ready.
  3. Flag gaps, do not fill them. Add a line to every prompt: "If something is missing or unclear, say so — do not estimate." This keeps every figure citable.
  4. Name the reader. "Draft an analysis for the underwriting committee" gets a different output than "summarize this file." The audience shapes the format and detail level. Put it in the prompt.
  5. One sentence beats a rewrite. When the first pass misses, add one corrective sentence and let it rerun. Redirect, do not take over.
01 — Pick your use case

A real job from your own week

Choose something repetitive and heavy on documents that ends in a deliverable. Put the files in a folder, then write the outcome in one sentence along with the test you'll judge it by.

Stage the work

Connect only the folder the task needs. You can seed from an Anthropic industry pack so you start with proven structure. Gen Re scenario: point Cowork at a legacy Excel/VBA model (the code plus what the team knows about how it's used) and ask for process documentation a new analyst could follow, plus a defect list for the modernization team. The responsible engineer reviews and signs off — Cowork drafts, it doesn't decide.

Write the acceptance test

Decide what "done" means before you start. You'll reuse this same deliverable and test in Workshop 3 when you turn the job into a repeatable skill.

✅
What a good acceptance test looks like

"The documentation covers every tab and every input the macro reads, walks the logic step by step in plain language, and flags at least three defects or risks with the line each lives on. Anything the source doesn't explain is marked as an open question. Nothing is invented." One or two sentences is enough. If you can read it at the end and know whether Cowork passed or failed, it works. Write it before you start. You'll reuse this same test in Workshop 3 when you turn the job into a skill.

Pick your track — ready-to-paste prompts

Pick the track that matches your work — Track 1 to generate documentation from a legacy model or script, Track 2 to run a technical review of working code — then copy its prompt. Both run fine against the same sample file.

Documentation generation. Point Cowork at a legacy model, script, or process you own — Excel/VBA, R, SQL, a config — plus any context about how it's used. No file of your own? Use the sample legacy model.

Track 1 prompt — paste into Cowork 
Read the legacy model in this folder and write process documentation a new analyst could follow: what each tab or component holds, what the code does step by step in plain language, every input it depends on and where it lives, and the business rules it implements. Then add a build-ready spec section for the team modernizing it: inputs, transformations, outputs. Cite the specific line or cell reference for every claim, mark anything the source doesn't explain as an open question, and treat it as a draft for the responsible engineer to sign off — not the final word.

Acceptance test: "The documentation covers every component and every input the code reads, explains the logic in plain language a new analyst could follow, and marks anything unexplained as an open question. Every claim cites a line or cell. Nothing is invented."

Technical review. Point Cowork at code you or your team maintain — a script, a module, a workbook macro — and ask for a second pair of eyes. No file of your own? Use the sample legacy model — it has planted defects to find.

Track 2 prompt — paste into Cowork 
Review the code in this folder for potential errors and improvement opportunities. For each finding: name the line or cell it lives on, state what could go wrong and under what conditions, rate how confident you are, and suggest a fix. Separate likely defects from style or robustness suggestions. If something looks wrong but you cannot be sure without more context, say so rather than asserting it. Format the output as a review a human reviewer will verify — you are an additional pair of eyes, not the final judgment.

Acceptance test: "The review lists findings with a specific location, a concrete failure scenario, and a suggested fix for each, separates likely defects from suggestions, and states its confidence honestly. Every finding is verifiable by a human reviewer. Nothing is asserted that the code doesn't support."

02 — Hand it off and steer

Sonnet, ask before acting, read the plan

Put Lesson 2 into practice. Start on Sonnet, keep approvals on, and read the plan before you let it run. Track what the task took so the value is easy to point to later.

Do

Hand off the whole task

Describe the outcome, let Cowork plan across the folder, approve the steps, and redirect with a sentence if it drifts. Don't reach in and take it over.

Direct the work; let Cowork do it.
Record

Time, rounds, and quality

Track three things while you run: how long the task took from start to finished deliverable, how many rounds of feedback it needed before the output passed your acceptance test, and how close the first pass came — would you have sent it as-is, or did it need a full revision? Write these down before you leave the lab. They are what you bring to Workshop 4 to show the value of this workflow and to seed the adoption dashboard. A finished deliverable with those three numbers is worth more than a dozen chat transcripts.
